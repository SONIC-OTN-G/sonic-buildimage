
### 三个场景,三条数据链

| 场景 | 一句话 | 数据链 | 看点 |
|:--|:--|:--|:--|
| 一 | 硬件读数自动进库 | daemon 轮询 → STATE_DB | timestamp 3 秒一跳 |
| 二 | 命令改硬件 → 框架自己反应 | thermalctl → 硬件 → thermalctld → STATE_DB 告警 | ≤3 秒告警翻转 |
| 三 | 业务数据采集+归档 | FLEX_COUNTER_DB 配置 → syncd C++ 线程 → COUNTERS_DB → 历史封存 | 8 键浮现、窗跨界封存 |

### 名词小词典(够用就好)

| 名词 | 白话 |
|:--|:--|
| STATE_DB | 「现在硬件什么状态」的展示库(温度/电源/风扇/告警) |
| FLEX_COUNTER_DB(db5) | 采集配置库:采什么、多久采一次、开不开 |
| COUNTERS_DB(db2) | 采集结果的「当前窗」:当刻值+滚动统计 |
| GB_COUNTERS_DB(db10) | 采集结果的「历史归档」:每窗口一笔定格(C++ 真件写这) |

| vid / rid | 同一个硬件对象的两套编号:vid=syncd 内部用,rid=vendor 库用,meta 库互译 |
| op 伫列 | 给 syncd 下指令的通道:LPUSH 一笔 op + PUBLISH 敲一下钟 |

## §1 场景一:PMON 轮询(daemon → STATE_DB)

### 1.1 这是什么

PMON 容器里的 daemon 定时读硬件(仿真环境=HalPlatformApiServer 模拟件),把读数写进 STATE_DB。**硬件没变,值就不动;但 timestamp 每轮都刷新——timestamp 跳,就是轮询管道活著的证据。**

```
psud ──3 秒──▶ PSU_INFO│PSU0          (电压/电流/功率)
thermalctld ──3 秒──▶ TEMPERATURE_INFO|System Board   (温度+门限+告警+timestamp)
```

### 1.2 演示步骤(3 分钟)

```bash
# ① 谁在跑
sudo docker exec pmon supervisorctl status          # psud/thermalctld/stormond RUNNING

# ② 看轮询成果
sonic-db-cli STATE_DB HGETALL 'TEMPERATURE_INFO|System Board'
#    预期:temperature=37.0, high_threshold=71.0, warning_status=False, timestamp=<当前时间>

# ③ 证明「在轮询」
watch -n 1 "date +%T; sonic-db-cli STATE_DB HGET 'TEMPERATURE_INFO|System Board' timestamp"
#    预期:timestamp 每 3 秒跳。Ctrl+C 退出。
```

**讲点**:值不动=硬件没变化;timestamp 3 秒跳=daemon 本轮重写了整行。想让「值」动?用命令动硬件——就是场景二。

### 1.3 相关改动

| 文件 | 改动 | 原因 |
|:--|:--|:--|
| pmon 容器 `/etc/supervisor/conf.d/*.conf`(thermalctld 段) | 启动参数加 `--thermal-monitor-update-interval 3`(原厂预设 60 秒) | 60 秒一跳现场等不起;3 秒节奏肉眼可见。容器层改动,重开机后要重套(§4) |

代码零改动——场景一纯框架内建能力。

## §2 场景二:PMON 设硬件数值(thermalctl 改门限 → 越限告警)

### 2.1 这是什么

`thermalctl` 是照 `psuutil`/`fanshow` 家族模式写的运维命令(命令 → sonic_platform 平台 API → 硬件)。这个家族原本全是唯读,thermalctl 补上「写入」:把高温门限从 71°C 降到 35°C(低于现值 37°C,制造越限)→ thermalctld 3 秒内轮询到 → STATE_DB 告警翻 True → 还原恢复。

```
thermalctl set-high-threshold ──▶ 模拟硬件(门限=35)
        thermalctld 3 秒轮询 ──▶ 37 > 35 越限 ──▶ warning_status=True
```

**诚实定位**(现场被问到再讲):这是平台层运维命令,不是 CONFIG_DB 管理面下发;风扇转速不会变(无策略引擎,thermalctld 只跑监控告警)。

### 2.2 演示步骤(3 分钟)

```bash
# ① 记基准
sudo thermalctl show                 # Board = 37 / 71 / 10.4 / False

# ② 命令下发:71 → 35
sudo thermalctl set-high-threshold "System Board" 35      # 预期:-> 35.0: OK

# ③ 看反应(≤3 秒)
watch -n 1 "sudo thermalctl show"    # HighThr 变 35、Warning 变 True。Ctrl+C。

# ④ 还原
sudo thermalctl set-high-threshold "System Board" 71
sudo thermalctl show                 # Warning 回 False
```

### 2.3 相关改动

| 文件 | 改动 | 原因 |
|:--|:--|:--|
| `src/sonic-utilities/scripts/thermalctl`(fork,gitlink b4802d16) | **新 CLI**:show / set-high-threshold / set-low-threshold | 现有 psuutil/fanshow 家族全唯读,演示需要「命令写硬件」;照家族正统模式写,即「加命令」参考范例 |

## §3 场景三:syncd 侧采集(C++ 采集器 → 当前窗 → 历史归档)

### 3.1 这是什么

syncd 进程内的 C++ 采集器(`OtaiGaugeCollector`)是 OTN 真件:**订阅 FLEX_COUNTER_DB,一个采集组一条线程**,组表定节奏与开关、counter 表定「哪个硬件对象、采哪些指标」。采到的读数写 COUNTERS_DB(当前窗滚动统计),窗口走完封存进 db10(历史定格)。

```
FLEX_COUNTER_DB(db5)          配置层:组行(节奏/开关)+ counter 行(对象+指标)
      ↓ syncd 订阅(事件驱动,配置一写即生效)
syncd 进程:C++ 采集线程(一组一条)──读模拟硬件──▶
COUNTERS_DB(db2)              当前窗:LINECARD:linecard1_Temperature:15_pm_current
      ↓ 窗口跨界(演示版 5 分钟,ITU-T 真值 15 分/24 时)
GB_COUNTERS_DB(db10)          历史:…15_pm_history_<窗起时间>,TTL 约 2 天
```

**为什么要「手工种配置」**:正常系统由 orchagent 按业务配置写 db5;本仿真无 orchagent,所以我们用 op 伫列协议手工模拟生产端(原理见 `43`)。**先得有硬件对象**(线卡)——手工 create 一次。

> python 桩(stub_collector)是 C++ 真件就位前的补位桩,架构位置相同、模型较简(单窗、写 db15)。真件已闭环,桩仅作对照基线,演示不再用它。

### 3.2 演示步骤(操作 4 分钟 + 等窗 5 分钟)

```bash
# ① 快检:syncd 活著、依赖完整
sudo docker exec syncd supervisorctl status | grep ^syncd        # RUNNING
sudo docker exec syncd ldd /usr/lib/x86_64-linux-gnu/libswsscommon.so.0.0.0 | grep -c "not found"
#    预期:0(非 0 = 三件套没套好,见 §4/44)

# ② 手工 create 线卡(必带 4 个通知指针,否则 10 秒后 SEGV)
redis-cli -n 1 LPUSH "ASIC_STATE_KEY_VALUE_OP_QUEUE" \
  "OTAI_OBJECT_TYPE_LINECARD:oid:0x1000000000000" \
  '["OTAI_LINECARD_ATTR_LINECARD_STATE_CHANGE_NOTIFY","0xdeadbeef","OTAI_LINECARD_ATTR_LINECARD_ALARM_NOTIFY","0xdeadbeef","OTAI_LINECARD_ATTR_LINECARD_OCM_SPECTRUM_POWER_NOTIFY","0xdeadbeef","OTAI_LINECARD_ATTR_LINECARD_OTDR_RESULT_NOTIFY","0xdeadbeef"]' \
  "Screate"
redis-cli -n 1 PUBLISH "ASIC_STATE_CHANNEL@1" "G"

# ③ 给线卡起个名(采集键名的来源)
redis-cli -n 2 HSET "COUNTERS_LINECARD_NAME_MAP" "oid:0x1000000000000" "linecard1"

# ④ 开采集组(组名含 1S_STAT_GAUGE 才会被采集器认;1 秒采样)
redis-cli -n 5 LPUSH "FLEX_COUNTER_GROUP_TABLE_KEY_VALUE_OP_QUEUE" "1S_STAT_GAUGE" \
  '["POLL_INTERVAL","1000","FLEX_COUNTER_STATUS","enable"]' "SSET"
redis-cli -n 5 PUBLISH "FLEX_COUNTER_GROUP_TABLE_CHANNEL@5" "G"

# ⑤ 指定采什么(线卡的 4 项 stat)
redis-cli -n 5 LPUSH "FLEX_COUNTER_TABLE_KEY_VALUE_OP_QUEUE" "1S_STAT_GAUGE:oid:0x1000000000000" \
  '["id_list","OTAI_LINECARD_STAT_TEMPERATURE,OTAI_LINECARD_STAT_CPU_UTILIZATION,OTAI_LINECARD_STAT_MEMORY_AVAILABLE,OTAI_LINECARD_STAT_MEMORY_UTILIZED"]' "SSET"
redis-cli -n 5 PUBLISH "FLEX_COUNTER_TABLE_CHANNEL@5" "G"

# ⑥ 看当前窗(等几秒)
sudo docker exec database redis-cli -n 2 --scan --pattern 'LINECARD:linecard1_*'
#    预期:8 键(4 stat × 15min/24h 双窗)
sudo docker exec database redis-cli -n 2 HGET "LINECARD:linecard1_Temperature:15_pm_current" instant
#    预期:35.0(与模拟硬件 json 一致;CPU 值目前型别错位,演示挑 Temperature/Memory 讲)

#    看整个对象(全部栏位,--json 出 JSON):
sudo docker exec database redis-cli --json -n 2 HGETALL "LINECARD:linecard1_Temperature:15_pm_current"
#    预期:{"interval":"300000000000",…,"instant":"35.0","avg":"35.0","current_validity":"complete",…}
#    讲点:interval 300000000000 ns = 5 分窗(补丁#5 生效)

# ⑦ 等窗口跨界(5 分钟整点,正好用来答问),看历史归档
sudo docker exec database redis-cli -n 10 --scan --pattern "*pm_history*" | head -3
#    预期:…15_pm_history_<窗起ns>;TTL≈2 天。**注意查 db10,不是 db15**
sudo docker exec database redis-cli --json -n 10 HGETALL "<上面扫到的 pm_history 键>"
#    预期:同款 JSON(max/min/avg/instant/max-time/min-time/interval/starttime/validity),多一个 TTL 归属
sudo grep -E "history write done" /var/log/syslog | tail -2
```

**讲点**:改 db5 配置 → 线程即开即停(配置驱动);COUNTERS_DB 是「滚动中的当前窗」,db10 是「走完的窗口定格」——ITU-T 的 15 分/24 时性能监视模型,演示版压成 5 分钟看得到封存。收尾:`FLEX_COUNTER_STATUS` 改 `disable` 同款 LPUSH 即停线程(数据冻结留库无妨)。

## §4 重开机后重套(照抄)

### 4.1 存活矩阵

| 资产 | VM 重启 | 容器重启 | 容器重建 | 备注 |
|:--|:--|:--|:--|:--|
| thermalctl(host /usr/local/bin) | ✅ | — | — | root 档案系统持久 |
| 三件套+boost、syncd 二进制、init 补丁 | ✅ | ✅ | ❌ | 容器层;重建才要重装(→`44`) |
| HISTORY_DB 映射(id15) | ❌ | ✅ | ❌ | tmpfs,开机重生成 |
| thermalctld 3 秒参数 | ❌ | ✅ | ❌ | pmon conf 开机被重渲染 |
| 场景三全部种子+采集数据 | ❌ | ✅ | ❌ | redis 无持久化,重种=重跑 §3.2 |

### 4.2 重套命令(只列必做;容器重建另加 `44` §2 三件套)

```bash
# ① HISTORY_DB 映射(VM host)
sudo python3 -c "
import json
p='/var/run/redis/sonic-db/database_config.json'
d=json.load(open(p))
if 'HISTORY_DB' not in d['DATABASES']:
    d['DATABASES']['HISTORY_DB']={'id':15,'separator':'|','instance':'redis'}
    json.dump(d,open(p,'w'),indent=4)
print('ok')"
sonic-db-cli HISTORY_DB PING        # True

# ② thermalctld 3 秒参数(必须 reread+update;restart 不重读 conf!)
sudo docker exec pmon sh -c "CONF=\$(grep -l 'program:thermalctld' /etc/supervisor/conf.d/*.conf); \
  grep -q 'update-interval 3' \$CONF || \
  sed -i 's|^command=python3 /usr/local/bin/thermalctld\$|& --thermal-monitor-update-interval 3|' \$CONF"
sudo docker exec pmon supervisorctl reread
sudo docker exec pmon supervisorctl update
sudo docker exec pmon supervisorctl start thermalctld   # update 后 autostart=false 不自启

# ③ 验证:场景一 watch 3 秒跳 → 场景三重跑 §3.2
```
