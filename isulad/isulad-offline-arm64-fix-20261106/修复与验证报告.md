# ARM64 iSulad 离线包修复及验证报告（20261106-r1）

## 交付结论

保留私有 rootfs/chroot 部署方式，修复 runc exec 根目录错位。已在本地 QEMU 全系统 ARM64 虚拟机、Linux 5.10.0-32-arm64（Debian 5.10.223-1）完成最终回归，退出码 0。
测试的 ARM64 runc 与交付包二进制 SHA256 完全相同。
这不是仅通过 qemu-user 运行版本号：ARM64 内核实际执行 namespace、cgroup v1、OverlayFS 与容器生命周期。
测试内核并非厂商专有 5.10.0 构建，目标设备仍需验收。未修改厂商设备，也未修改旧离线包。

## 故障机制与直接修复

已观察到 exec/main 的 mount namespace 相同，exec 根目录却与设备相同。外层 chroot 将进程根目录和命名空间挂载树根分离；当前 runc exec 的 setns 路径不会复制主进程独立设置的 chroot。
启动容器时 rootfs 初始化成功，exec 时没有恢复同一根目录，因而看到厂商文件、找不到 Debian 镜像内 redis-cli。
本地同版 runc 已复现，且外层 chroot 下正常 pivot 路径也可出错，因此不能简单声称只禁用 no-pivot 即可修好。

修复在 runc 内部完成，不依赖业务 shell/chroot 命令，也不改变 isula exec 的用户接口：
1. 可信父进程通过 procfs 引用打开容器主进程的实际 root，前后校验 init 启动时间与存活。
2. 通过内部继承描述符传给单线程 nsexec 阶段，不把路径或 PID 留到错误的 /proc 环境中解析。
3. 加入命名空间后，执行 fchdir(rootfd)、chroot(".")、chdir("/")。
4. 立即关闭根目录描述符，继续原有用户/工作目录/能力/seccomp 设置。
5. 失败即终止，并清理启动前错误路径的日志管道，不能继续在宿主根执行。

源码位置：runc/libcontainer/process_linux.go 的 setnsProcess.start；runc/libcontainer/nsenter/nsexec.c 的命名空间加入后段。
两个代码段均有 SONIC-OFFLINE 注释解释厂商设备 chroot 场景、PID/proc 不一致和描述符关闭要求。
本补丁是本项目适配，不宣称已被上游合并。

## 合并的设备适配

| 问题 | 本版处理 | 代码 |
|---|---|---|
| exec 看见设备 root，找不到 redis-cli | 在运行时中恢复 init root，保留原权限/安全设置 | runc 的上述两处源码 |
| devices 内核启用但未挂载 | 在私有 mount namespace 内挂载；不可用明确失败 | scripts/ns-start.sh |
| cpu/cpuacct 挂在 /ofs1 等非标准目录 | 发现真实来源，保持一个 cpu,cpuacct 挂载，创建 cpu/cpuacct 相对别名 | scripts/ns-start.sh |
| 重复将联合控制器拆成 cpu 和 cpuacct，runc 挂载 EPERM | 按真实控制器组合命名挂载点，不重复拆分 | scripts/ns-start.sh |
| 初始 rootfs 上 pivot_root 返回 EINVAL | 对 create/run 明确添加 --no-pivot；exec 由源码补丁独立处理 | rootfs/usr/bin/runc |
| /dev/shm bind 出现无效 size= | 保留原有仅删除该 bind 选项的兼容适配 | rootfs/usr/bin/runc |
| OverlayFS 缺失 | 启动前明确报错；显式辅助加载匹配厂商 ko，不伪造内核能力 | control.sh、scripts/load-overlay.sh |
| isulad_tmpdir 不存在 | 创建 data/isulad_tmpdir，root:root、0700 | control.sh |
| 精简 /dev 缺 /dev/fd | 测试日志改为直接写文件，取消 Bash 进程替换 | 两个业务测试脚本 |
| 宿主 PATH 没有 gzip | 诊断收集显式调用包内 BusyBox tar/gzip，逐步检查失败 | control.sh collect |
| 系统没有 sha256sum、修改后旧清单不匹配 | 提供包内 BusyBox 校验入口，重新生成完整校验清单 | verify.sh、SHA256SUMS |
| 避免 exec 的业务参数 run/create 被误识别 | 仅解析真正的运行时子命令 | rootfs/usr/bin/runc |

所有特殊处理处均添加了原因注释。cgroup 挂载可见性隔离不等于复制内核：控制器层级仍是共享内核状态；本版不卸载设备已有的 cpu/cpuacct 挂载。
lws_vhost_destroy2/protocol destroy 之前只是清理日志，没有足够证据说明它是独立根因，因此没有添加掩盖错误的处理。

## 仿真环境

- QEMU qemu-system-aarch64，TCG，cortex-a72，4 vCPU、4 GiB 配置内存。
- ARM64 Linux 5.10.0-32-arm64，初始 / 保持为 initramfs 的 rootfs，不 switch_root 到普通磁盘根。
- 宿主 /etc/os-release 标识为 Simulated vendor initramfs。
- ext4 虚拟数据盘挂 /ofs1；离线包位于 /ofs1/isulad-offline-arm64。
- 宿主仅预挂载 cpu,cpuacct 于 /ofs1/vendor-cgroups/cpu；devices 未预挂载。
- 首先保持 overlay 模块未加载，确认 start 明确拒绝；然后加载虚拟机内核匹配的模块。
- 宿主没有 yum/sudo/Python 环境依赖，也没有 /dev/fd 和 gzip 命令入口；包内用户态仍提供自身工具。
- 业务镜像沿用 20261022/20261023 的原始三个 ARM64 tar.gz，没有重建或重新打包业务镜像。

## 迭代中发现的问题

初次使用的 6.12 仿真内核将部分 cgroup 控制器配置为 v2-only，enabled=1 并不保证可挂载成 v1；增加非必需控制器告警跳过，随后使用更接近设备的 5.10 做最终回归。
最小虚拟设备缺 /dev/fd 与 gzip，分别暴露业务测试重定向和诊断收集问题，均已修复。
一次离线编辑未清理日志的虚拟 ext4 后，日志回放造成测试脚本截断；重建测试磁盘并核对脚本字节后消除。它属于本地仿真制备问题，不是设备或镜像缺陷。
最后一轮使用最终运行代码重新执行全部业务测试，不能将中间失败试验当成最终结果。
